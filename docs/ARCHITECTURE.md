# Architecture

One Rust process, the core, holds the map and talks to Meta's models; one web page per window draws it. They share a WebSocket. Paths below are under `core/src` and `ui/src`.

## The shell

`shell/flag.ts` makes this layout the default page. `?shell=1` opens the classic page instead (the header and bottom bar, kept for one more release), and so does `?cards`, the classic page opened on Cards; `?shell=2`, the shell's old address, still opens the shell, even beside `?cards`. The features playground (`bricks.html`) is not the app's page and keeps the classic look. `App.tsx` keeps the same core, map, mic, input box actions and feature host for both returns. Its shell return assembles the corners, map view, stage, held stack, status line and tabbed rail using the exports above. It opens on the Canvas, shows `Welcome` after an empty snapshot, and uses the Features page's Show actions for enabled alternate views. App owns the stage's cards, notice/map update, `#shell-caption` host and input box. It measures the shelf and held stack so the bottom-right stack and rail clear them, and invokes the Deadlines placement hook. The existing `data-slot` markers and their layout-dependent presence are listed in [Features](bricks.md#slots).

App connects Features page requests to the Features tab, “what just happened?” to History, and Help to Settings. `useHistory` records activity in this window from opening, with Show and available Undo actions; it is not a saved map log. The shell makes Canvas, Fly-in, Tiny transcript and Notification history built in through `CORE_BRICKS`; it uses History in place of mounting the Notification history panel. Other features and the built-in feature switches feed the Features tab's rows.

`Guide.tsx` supplies the held cards and caption content. It asks one waiting item after a 2.5 s natural pause with no unfinished draft or open dialog, while the page is visible and no caption is up. Urgent questions come first. The held card can ask now, wait for later or drop an item; talking over a caption returns its unread words to the stack. This state belongs to the receiving window, outside the saved map.

The shell's `Rail` starts closed. Outside a call, its Talk tab uses `TalkTurns`: the last 60 thoughts with nonempty text, oldest first, with speaker and time. In a call (`talk/call-core.ts`'s `inCall`), App removes that tab and closes it if selected; `talk/TalkRail.tsx` independently hosts the full `Talk` UI. TalkRail opens by default on a wide screen with at least two people (a Remote, listed in the Share menu as a device, is never one), stays closed by default with one person and an AI participant, and uses a sheet on a phone. Its pill reopens it and shows unread turns. Both open rails use `data-slot="rail"`; the call rail and another shell tab can be mounted together.

## Guide relay and runtime jobs

`protocol.rs` defines the existing WebSocket messages; `main.rs` dispatches them to `guide.rs`. They do not change `World`, write the journal or start model work. The core adds the sender's identity on the shared map (`by`) and server time (`at_ms`). Live point/caption/hold, tour and job messages go to every window except the originating window, including other windows of the same speaker. Answers use the recipient route instead.

| Sent by a window | Core behavior |
|---|---|
| `point { target?, caption? }` | Relays `guide` with `kind: "point"`. A target is an existing `data-guide` name to look up in the receiving page; the core validates its syntax, not whether it is on screen. Caption: at most 140 characters. Null or omitted target takes the sender's point down and discards its caption. |
| `caption { text }` | Relays `guide` with `kind: "caption"`, no target; requires nonempty text, at most 400 characters. Guide draws it above the input box, or holds it while the person is busy. |
| `hold { text, target?, urgent? }` | Relays `guide` with `kind: "hold"`; at most 140 characters, optional target for when asked. `urgent` moves it ahead of other waiting questions at the next pause. Empty text takes back that sender's held items and question being asked. Each receiving window owns the pause/held state; Guide projects its cards into `shell/held.ts` in the shell. |
| `tour { steps }` | Validates the whole ordered list before relaying `tour`: at most 20 steps, each with nonempty text of at most 140 characters and an optional target. Empty steps clear the sender's tour. This is relay only; the current guide receiver handles `guide` messages, without tour playback. |
| `job { id, title, status, result?, parent?, demo? }` | Relays a flat `job` update and retains the latest accepted state per id in core memory. Title: nonempty, at most 80 characters; result: at most 160. Status: running, done, failed or waiting; demo defaults false. Id and optional parent use the same syntax as target names. |
| `answer { to, text }` | Normalizes `to` as a shared-map speaker name (whitespace collapsed, controls removed, at most 24 characters), requires a nonempty recipient and text of at most 280 characters, then sends `answer { by, text, at_ms }` only to that recipient's windows, including the origin when answering oneself. It does not use screen-target syntax or broadcast the answer to the shared map. |

Text is normalized to one line before length checks. Target names allow 1–100 ASCII letters, digits, `:`, `-`, `_` or `.`. All six message kinds share a limit of four accepted messages per second per window (a whole tour counts once); refusals go only to the sender's windows as `Not shown: …`, at most once a second. Malformed job/answer fields use that same refusal route.

Points, captions, held questions, tours and answers are transient and have no reconnect replay. Jobs also never persist to disk, but survive window disconnects while the core runs: `guide::Runtime` retains at most 60 distinct ids in first-appearance order, replaces an existing id in place, and evicts the oldest row for a new id past the cap. `main.rs` subscribes and captures job replay under the publication lock, sends the snapshot and placing state before the latest jobs, then forwards newer updates. Lag recovery repeats that catch-up, skips queued jobs superseded by replay, and keeps forwarding buffered non-job messages, including recipient-only answers. Restarting the core clears the jobs. `ui/src/work-jobs.ts` keeps the connection's job list outside the map for `map.jobs`; `core.ts` resets it on each snapshot before replay, and start/end times derive only from states this window saw.

## State and the journal

- `World`: its topics (`threads`), thoughts, `active` (where the talk is), `active_by` (each speaker's topic), suggestions, actions, `merged` (old topic id to its successor), apps, recaps, `positions` (topic or thought id to where it was put on the canvas, by whom and when).
- Every change goes through `Core::commit`: under the world and journal locks, each `Change` is applied to the `World` and appended to `data/<map>/journal.jsonl` as one JSON line (`#[serde(tag = "type")]`); then each is broadcast as `ServerMsg::Change`. Nothing else changes the `World`, but a place on the canvas (`positions::set`): applied and broadcast the same way, under the same locks, while its journal line may wait up to 250 ms for a newer step of the same item to take its place (a drag sends one every frame). A commit drops a waiting line whose item it takes off the map, so replay matches what windows were sent.
- `Core::record` appends a change that only the journal keeps (`ExplainAnswered`, `AnswerMarked`): the `World` ignores it and no window is sent it. These are labels for judging Explain and Recap prompts later.
- On start, `Journal::open` replays the file. A line it can't parse is skipped with a warning; a missing final newline (a crash mid-write) is added, so the next change starts on its own line. Fields added later carry `#[serde(default)]`, so old journals keep loading.
- A merge moves thoughts, tangents, suggestions, actions and each speaker's place, and records `from → into`; later changes aimed at `from` follow it, with a hop limit so a cycle can't loop.
- Each window keeps its own copy: a snapshot on connect, then every `Change`. If a window falls too far behind the broadcast queue, it gets a fresh snapshot plus the current app build and its own import status, so it catches up with the current world.
- Topic ids: `T1`, `T2`… from the placer (never reused: topics plus merges plus one); `I1`, `I2`… from imports; app cards with no topic land in `apps-output` ("Apps").

## Life of a spoken thought

1. `mic.ts` sends each 80 ms frame up the WebSocket as binary. It also sends a loudness reading every 320 ms, the RMS of those four frames (`apps-audio.ts`), for volume watchers; `?level` in the address shows each reading.
2. `asr.rs`: when a window turns its mic on, the core opens `wss://api.meta.ai/v1/asr/realtime` for it (the key in the handshake; endpointing, English bias, keywords, progress reports) and forwards frames; connect, handshake and every event after must come within 3.8 s (`QUIET_MAX`), or the stream ends as stopped. `transcript` events go back as live words to that speaker's windows; `speechComplete` calls `Core::add_thought`; a spoken "stop listening" ends the stream there, so nothing the service still sends after it is kept.
3. `add_thought` first lets a spoken yes, no or short fix answer the AI's open question on the speaker's latest thought (`catalog::answer`; a yes only ever answers that, never an outside action). Then it checks whole-turn commands (`Core::request`, which says what each did and how to undo it, `catalog::Done`; every act has one definition in `catalog::CATALOG`, held to the rules by a test) (recap, "make an app…", a view such as "pictures" or "let's focus", or Help ("what can I say?", "help"), sent only to the speaker's windows, "new topic", which marks the speaker's next thought to start a topic whatever the placer answers, the command pack in `spoken.rs` (each only as the whole turn: "add … to X" commits the thought already placed, with what to add as its point, when X is a topic's title or a kind of place no topic has yet, else it's a thought; "new topic about …" commits a topic titled from the words after it with those words as its first thought, already placed; a topic either starts gets an `S<n>` id, apart from the placer's `T<n>` (a placement still waiting on the model counts from an older map) and imports' `I<n>`, and leaving a topic whose last words trailed off marks it dropped, as `decide` does; "what was I thinking?" is "where was I?"; "forget it", "later", "finish it" and "stop listening" are `View`s the window acts on, since it knows which Unfinished thought card it shows; "expand …" sends `Unfold`; "add it to Reminders" approves as a click does, host only; "keep it" decides a waiting build), and "where did I talk about …?" or "go to the one about …"; "find", "take me to" and "go to" only when they point at the map, since they also start to-dos). Every request skips the same words before it (`lead_in`: what `filler` sets aside, "now", "hey", "please" and "can/could/would/will you"; "I see", "I mean", "you know" and "like" only before a pause mark, since without one they make a sentence of what follows: "I see the pictures"); partway through a turn "would you go back?" asks someone, so those four don't lead in there, and the unpunctuated end-of-turn scan for "where was I" skips nothing, so the word before it stays in the thought. A search's question is the turn's first sentence (the dot of a title or initials, "Dr." or "U.S.", doesn't end it; that of "example.com." or "v2.1." does): a jump or a notice that says why not (empty map, no key, nothing found, the call failed) answers it, never a thought; the words said after the question are then handled as a turn of their own, and a "take me back to …" with nothing pointing at the map (no "the topic about …", no #tag) is kept as a thought when nothing matches, since it may be a saying. While the model looks, "Looking through your topics…" stays up; newer words or a move stop the search, keep its words first and send an empty notice that takes it down; a search those words ask stops as it's asked, since it was asked before the newer words or move and its answer would undo them. "Where was I?", "next one" and "last one" can also appear at the end after a pause; words before them are kept as a thought, and the command waits in the placer's line behind them. A command acts at once when none of the speaker's own words are waiting for their first try: it never waits for another speaker's words or for a retry. "Where was I?" goes to the topic where the speaker's last line trailed off, even the one they're on, else the one they dropped last, else back from a detour (one line away from the topic they're on, or a topic reached without speaking: `way_back`); with none of those it sends a jump to the speaker's newest point on the topic they're on ("You're on …") or a notice saying why there's nowhere to go, and "next one" and "last one" say so on an empty map or the only topic. Before creating a thought, it sets aside filler such as "um, so" and acknowledgements such as "yeah, okay" unless the latest thought ended with a question mark. A turn no request reads may correct the speaker's previous one, said within `JUST_BEFORE_MS` (`catalog::correct`): “scratch that” runs that turn's undo, or takes its words off (`ThoughtSkipped`; Undo re-adds them); “No, I meant …” undoes a previous request, then runs the request named, read by rule, else by one model call (the placer's model, minimal reasoning, 12 s) that sees the previous turn, what the app did, the topic titles and the command list's acts it may pick, and answers one act and a phrase, which runs only if `catalog::classify` reads the phrase as that act; words kept from the previous turn come off once the request acts (a search: once it jumps, `catalog::searched`), and a topic they alone started goes with them (merged where the speaker was, else `ThreadRemoved`), with the topic's `last_point` recomputed. A view or fold is undone by `ServerMsg::Revert`: the window keeps what it showed before each voice view or fold. A model answer that arrives after a newer turn of the speaker's is dropped. Words put back that weren't placed are queued again, and a placement whose words were taken off while the model thought commits nothing (`Core::commit_if`). Each turn is remembered per speaker as a request (with its undo) or kept words, and the speaker's windows are told how long it can be corrected and where undoing it moves them (`ServerMsg::Correctable`), so the "this" mark previews a correction on the card the redo will act on. Otherwise it commits a `Thought` (`th-<uuid>`, the speaker's active topic, `placed: false`) and queues its id.
4. `placer.rs` takes one id at a time. The prompt puts the fixed instructions first (for the prompt cache), then each topic as `id: title [open|dropped] last: points` (its last `POINTS` points, oldest first, on the `RECENT` topics touched last, else its last point), oldest-touched first so a placement rewrites only the end of the list, the speaker's active topic, their previous turn as said with its topic when it came within 2 minutes (`JUST_BEFORE_MS`; not when it's the question just asked) and the thought. The instructions have the model find the thought's main subject first, reading to the end, and continue or return only when that topic's title covers it as it is (one that would need a wider title is a new topic, even on the same project); words that announce a move usually start one. If a turn moves to another topic, the answer quotes where it starts; the core cuts there, removes joining words at the cut, and queues the rest after the first part; the rest's prompt says it was cut where it moved on from the first part's topic. The model can skip short filler turns (up to 8 words); longer turns are placed, and so is a short turn right after a question (`just_asked`: it answers it). JSON schema answer, minimal reasoning, room for 2,000 tokens (two a character for a turn over 1,000 characters, at most 12,000), 20 s timeout (4 s and 8 ms a token of room); an answer cut off at its room is asked once more with twice the room. Two calls race (`RACE`, `PLACER_RACE`), lane i to the (i mod n)th model of `MODELS` (`PLACER_MODELS`, default Spark 1.3 then Spark 1.2; `PLACER_MODEL` puts its one model in every lane, as is), and the first good answer wins: the time is nearly all reasoning, whose length varies call to call, and a slow spell mostly hits one model at a time; each listed Contributor model keeps its own fallback; only one goes (lane 0) when the hourly cap has no room for both, and the dropped one is traced as dropped. `Route::Decided` names the winning lane's model. A thought whose words say it decided something (`decided.rs`, read on from the head it carries on across a pause) is placed with `decided`, and one the model would start as a tangent of a topic lands on that topic instead; words that say a decision are never skipped as filler, and a correction or a join taken apart reads the mark again (`ThoughtDecided`). The first try gets 6 ms a token of room (12 s for a short turn: 1.2 times filling the room, above every placement measured, n=1,015, slowest 11.0 s), later tries the full time. A failed try sends the thought to the back of the line 0.5 s, then 1 s, later, so a stall never holds up what was said after it; the third failure is said once, and it goes back 15 s later (doubling to 4 min), so an outage doesn't leave it unplaced until a restart; a busy service (429) holds the whole line for that wait, and a try refused by the hourly call cap skips the quick retries and waits for the next round. A command waiting in the line acts as soon as none of its speaker's words ahead of it are on their first try. A thought that lands after its speaker moved on (newer words of theirs landed, or they moved while it retried) goes on the map without moving them or marking topics they left. The core sends `placing` (the thought in flight, and each retry with its wait) on every change and on connect, for the placing pills. <!-- names-ok: "room" is the ordinary word here (headroom for a model answer), not a shared map -->
5. `decide` trusts only ids that exist. It builds `ThreadAdded` (for a new topic, with its parent if that exists), `ThoughtPlaced` (with a sure fix applied, or the question to ask), `ThreadTouched`, drops and `ActiveChanged`, and commits them together. Drops are the speaker's own: a topic they left whose last thought trailed off, or one the model names that they spoke on.
   A thought that carries on words cut off by a pause (`chunks.rs`): `request` also quotes the speaker's latest turn that trailed off when it's still the last word on its topic and was said within `JUST_BEFORE_MS` or is on the topic they're on (`chunks::heads`); the answer's `joins` ("before", "unfinished" or "none") names one of the two, and `decide` then places it on that topic whatever the action, unless the speaker asked for a new topic; only a turn said strictly earlier counts, so a split turn's rest can't carry on its own first part. The answer's `assumed` is kept only when the placement moved the thought from the speaker's topic (a tangent of it doesn't count, `chunks::moved`). Both go in one `ThoughtNoted { thought_id, note }` after `ThoughtPlaced`, kept in `World::notes` by thought id (not on `Thought`, so its many literals stay as they are); `ClientMsg::Unlink` takes the link off and `ThoughtRepointed` puts the later one's own words back as its point. A head has at most one carrier (`chunks::carriers`); a correction to a head swaps the same words in its carrier's point; a skipped thought keeps its note, so Undo brings the link back. The UI's `asIdeas` shows a carried-on thought inside the later one, at the later one's place.
6. In the UI the placing pill and the placed point share a Motion `layoutId`, so the thought moves from the bottom bar to its topic. An `ActiveChanged` in the commit that placed the speaker's own words (after its `ThoughtPlaced`, `ThreadTouched` and drops) is their words moving them, even to where they'd already clicked, since `decide` sees the map from before the model answered; so is an import opening them on its newest topic when they had no place yet. Any other one for them, a `Found`, an `Unfold` or a `View` (but Later, Forget and Pause, which leave the map as it is), answers a request, and the window closes an open Recap so the result shows (`movesAsked` in `core.ts`).
   The map's follow tells `Attention.tsx` what it showed (the point gets the one highlight, `look`, once it holds still, for its reading time: 200 ms to look over plus 238 words a minute) or held back (the bottom bar's "New in X ↓"). Every other jump (Take me there, Since you left rows, Recap links, Finish it) calls the same `look`. Under Reduce Motion the point fades in for 200 ms where the slide would jump. Topics changed out of sight (not by your own words landing) get an unseen dot until the change has been readable on screen for its reading time, or you touch the topic.
7. `apps.rs` sees the `ThoughtPlaced` broadcast and runs matching watchers; the refiner and pictures pick the thought up at the next pause.
8. When a window returns after at least 30 seconds hidden or blurred, `Away.tsx` compares the map before and after the absence. It shows the speaker's newly placed thoughts grouped by topic, and new proposals on those topics; rows link to the point or proposal, and the card states this rule. It does not make a model call.

## The gate

`gate` in `main.rs` runs before every route and gives each request one of three levels: refused (403), the page only, or the map.
- Host: must be `localhost`, `127.0.0.1` or `[::1]` when the connection comes from this machine, or, on a shared map, the exact address and port the connection reached. A name a site could point at this laptop never passes, which stops DNS rebinding.
- Origin, when present: a page on this machine for a local connection, or, on a shared map, the listener's scheme (`https://` on the HTTPS listener, else `http://`) plus the Host. Browsers always send it on a WebSocket handshake, so another site can't open `/ws`.
- On a shared map, a connection from another machine without the code gets only the page's own files (`/`, `/index.html`, `/room`, `/pcm-worklet.js`, `/assets/*`); with it, everything else (`/ws`, `/images`, …). The code comes from `?room=` or a `room` cookie, is compared as lowercase letters and digits, in constant time.
- Every response that passes carries `Cross-Origin-Resource-Policy: same-origin`. Approving actions and importing also need a connection from this machine.
- Hashed files under `/assets/` and images get `Cache-Control: public, max-age=31536000, immutable`; pages and other responses get `no-cache`. A missing file that falls back to the page also gets `no-cache`, so an update is checked before the old page can be reused.
- With no model key, the core sends a notice when a window connects. The header says "No AI key"; the map remains browseable, and typed thoughts are labeled "Needs the AI key" without placement retries.

## Shared maps

- `ROOM_CODE` binds the core to `0.0.0.0`; without it, to `127.0.0.1`.
- With `ROOM_HTTPS=1` too (`./run.sh room` sets it; `ROOM_HTTPS=0` turns it off), the host keeps plain HTTP on `127.0.0.1` and guests get HTTPS on the laptop's network address, the same port, so a guest's browser treats the page as secure and lets its mic work. The certificate names that address, this machine's name and localhost, and is reused across restarts.
- Each outgoing message goes to every window or to one speaker's windows: live words, mic status, "Back to …" notes, Recap progress and import progress go only to their speaker.
- Per speaker: the active topic (`active_by`), who dropped a topic (`dropped_by`), the way back, and what the placer sees as "active".
- Another laptop that asks for no name, or for "you" (the host's own name), joins as "Guest" and is told so.
- Tunnel mode (`PUBLIC_URL`, set by `scripts/trial.sh`; it needs `ROOM_CODE` of at least 10 characters): the core binds `127.0.0.1` only and a Cloudflare quick tunnel on this machine forwards to it, so every request arrives from `127.0.0.1`. The gate then takes only requests whose Host is the tunnel's, whose Origin (when present) is `PUBLIC_URL`, and whose `cf-connecting-ip` (set by Cloudflare, which refuses a request that already carries one) names a visitor that isn't this machine; anything else, this laptop's own `localhost` included, gets 403. The map still needs the code. After the gate the request counts as coming from the visitor's address, so no one is the host: no approving into this laptop's apps, no imports, and "you" is renamed "Guest". `/room` says `tunnel: true`, and the join card reads as one person's own map.
- Every window gets a WebSocket ping every 30 s: a Cloudflare tunnel cut a silent socket at 125 s and held one with a 30 s ping.
- A name is the host's or a guest's, never both: another laptop can't take a name this machine's windows joined with (until the core stops), and this machine can't take one another laptop's window is using. `/room?name=` says so (`taken`), the WebSocket is refused (409), and the page asks for another name. Only the host stops an import.

## Import

1. `POST /import` (host only, needs a key, one at a time, up to 100 MB) parses a ChatGPT export (in each chat, the branch the person saw last), a Claude export, or a plain list or JSON Lines of messages. It keeps the person's latest messages up to 300,000 characters (each cut at 2,000, with 240 characters of the AI's reply as context), skips messages whose time is already on the map or in `MessagesRead` (what an import finished reading, including messages that gave no point, so the same file twice adds nothing), packs them into parts of up to 8,000 characters and 12 messages (bigger parts lose messages: see `PART_MESSAGES`), and returns a preview with the models and a cost estimate. Nothing is sent yet. <!-- names-ok: a ChatGPT chat's own branch, not a tangent -->
2. `import_start`: the ideas model reads six parts at a time; each idea is a subject (`topic` in code), a point, the person's own words, a kind and maybe a date. Ideas are grouped by subject name.
3. The grouping model sees the subjects with their latest points, the open questions, the tasks and the map's topic titles, never the messages. It returns topics (one level of tangents, or an existing topic), at most one question per topic, and tasks. Only subjects and topics that exist are trusted; a subject it leaves out becomes its own topic; if grouping fails, every subject does.
4. Topics land one at a time as `ThreadAdded`, `ThoughtAdded` (already placed, with the message's own time), `SuggestionAdded` and `ActionProposed`, then `MessagesRead`. `import_cancel` stops it; what landed stays.

## Adding an app block

- Watcher: a variant in `Watcher` (`apps.rs`); fire it in `on_thought` (thought watchers), the 1 s tick in `run` (timers) or `volume` (audio); bounds in `validate`; the schema in `composition_schema` and a line in the composer prompt (`COMPOSE`; `compose_prompt` fills in the volume scale); in the UI, the `Watcher` type in `apps-core.ts` and its label in `watching` (`Apps.tsx`). <!-- names-ok: the app composer is a model call, not the input box -->
- Publisher: a variant in `Publisher`; publish it in `execute`; template checks in `validate`; schema and prompt as above; its label in `Blocks` (`Apps.tsx`).
- Apps are journaled as `AppRegistered`, and app types use `deny_unknown_fields`. An older build can't parse a line with a block or field it doesn't know, and skips it with a warning.
